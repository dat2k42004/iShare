|---|---|

| `FR-<MOD>-###.n` | Sub-requirement |

| `ERR-<MOD>-###` | Error case |

| `QA-###` | Interview Q&A — traceability source for requirements |
| `ASM-###` | Assumption |
| `DEC-###` | Decision |

> IDs are **permanent**. They are never renumbered — deprecated entries are marked `[DEPRECATED]`.

## Traceability

Every functional requirement (`FR-###`) carries a `Source` field pointing to either:
- `DRAFT §x.y` — requirement derived from the product idea draft
- `QA-###` — requirement confirmed through a stakeholder interview answer (see QA Log in `.agents/.claude/system_analysis/output/registers/qa-log.md`)

A requirement with no source is a defect — report it as an `OPEN-###`.

## For the HMI / Screen Specification Phase

Each feature spec includes a **"Notes for HMI/screen spec"** column in its traceability matrix (Section 15).
That column flags what the screen designer must decide: which data to surface, what states to show, what flows to support — expressed behaviourally, never as layout or widget prescriptions.

Start the HMI phase from those notes + the FRs, not from the prose descriptions.
